日期：2026-11-19（香港）。對象：[QuantumPrediction/DoggyKnight](https://github.com/QuantumPrediction/DoggyKnight)，[草稿 PR #11](https://github.com/QuantumPrediction/DoggyKnight/pull/11)。

## 1. 建議決策

先完成「玩家能保留成果、願意換一種打法再玩」的第一章 Demo。開發順序為：完整冒險存檔 → 首三分鐘與戰鬥辨識 → 職業路線 → 同伴連攜 → 關卡選擇 → 平台與市場驗證。先把已有六章的第一章變得足夠好，再根據試玩證據擴展到其餘章節。

建議定位：

**帶領金毛與圓桌狗狗夥伴，靠走位、停步攻擊與同伴連攜，在繪本世界組成每局不同的冒險隊伍。**

這是待驗證的產品主張。可愛造型負責第一眼吸引；配搭和戰術選擇負責重玩；夥伴互動、救援與幽默負責記憶點。

目前 Windows 接手工作已存在，建議以 Steam 的完整付費遊戲／免費 Demo 為第一條驗證路線，同時保留手機觸控核心。這是基於本專案進度與建議商業模式的選擇，並非判斷 Steam 一定比 App Store 容易成功。手機保留直向短關卡、可靠中斷續玩；兩個平台的展示與操作分別設計。

## 4. 0.4 Demo 的具體設計

### P0：保存完整冒險成果

**目標：**玩家可以放心停下，再回來延續原來的配搭。

建議先做到安全波次／關卡檢查點恢復。中斷當前波時，從最近安全檢查點重新開始該波；介面明確顯示恢復位置。

待新增的冒險存檔資料包括職業、等級、經驗、把戲及進化、事件效果、活力、下一關加成、已選路線、進度及隨機狀態。永久成長與當局狀態分開，並把獎勵結算和檢查點作為一致的狀態保存，避免重載重複領取零食／寶箱。

驗收：關卡中、升級選擇、事件選擇、過關結算、營地及背景切換後重新開啟，配搭與進度均按定義恢復；重載不能刷新已提供選項或重複領獎；v1–v7 舊檔仍可讀。舊檔沒有記錄的把戲無法憑空還原，必須有清楚、有限的一次性相容行為。無盡模式也需要明確的恢復規則。

### P1：每職業兩條真正改變操作的路線

下表都是待測試機制，數值應在資料檔中調整。

| 職業／路線 | 玩家每幾秒要做的決定 | 得到甚麼 | 付出的代價 |
| --- | --- | --- | --- |
| 騎士・守護反擊 | 留在夥伴護盾附近，等待成功防禦後停步反擊 | 可見的反擊窗口、短距離範圍斬 | 主動追殺及遠處清怪效率較低 |
| 騎士・突進追擊 | 繞開預警後切入，挑選可擊倒的目標 | 擊倒延續連擊、短程突進 | 切入位置危險，沒有長時間防禦增益 |
| 法師・聚怪爆發 | 誘導敵群進入落點，再停步施法 | 大範圍連鎖爆炸 | 單體與高機動敵人的效率較低 |
| 法師・符陣控制 | 安排法陣位置，移動拉開再回到施法窗口 | 減速、延遲觸發及持續區域壓力 | 即時爆發較低，需要敵人留在區域內 |
| 弓箭手・專注狙擊 | 找安全站位，決定何時打斷蓄勢避險 | 強化單體、破綻傷害 | 站定時間與狹窄火力方向帶來風險 |
| 弓箭手・游擊穿透 | 不斷換角度，停步射穿排成線的敵人 | 穿透、移位後短窗口增益 | 單箭傷害或最大專注倍率較低 |

先讓每條路線有三個核心改變，六條共 18 個核心升級節點，並沿用現有共通把戲。這是規模上限提案，不是先堆滿卡片的交付要求。

抽選要理解職業適用性、必要前置、互斥核心、已取得效果；前兩次有意義的升級應能建立打法方向，後續仍有補防守、成形或冒險輸出的選擇。進化卡說清楚觸發方式與代價，避免只有百分比不同。

驗收：相同職業選兩條路線時，走位、有效輸出距離、站定時間或目標優先級至少有可觀察差異。玩家能說出自己為何這樣選；不以「卡片數夠多」視作完成。

### P2：把同伴連攜變成看得懂的特色

先利用已存在的貝德維爾擋箭與嘲諷，原型化一個「成功擋箭 → 玩家在短窗口停步攻擊 → 合作技」回路。分職業給出清晰但有限的變化：騎士反擊、法師折射法球、弓箭手反擊箭。

啟動必須有圖形與音效提示；新玩家不需要背配方。利用走位與停步觸發，先控制額外按鈕數量。同伴原有跟隨／格擋仍有效，連攜機制另設冷卻，避免無限觸發。

後續再測蘭斯洛特標記、高文破勢與崔斯坦節奏窗口。故事模式維持角色出場脈絡；自由搭配可先在獨立挑戰規則中測試，確認頭目破盾、缺同伴及倒下恢復不會卡關。

驗收：玩家能辨認何時發生合作技、自己做了甚麼；同伴不能遮住主要預警，也不能把所有選擇變成站在盾後最安全。

### P3：關卡有可操作的變化，難度有節奏

先重做第一章的兩至三個遭遇模組：

- **麥田救援：**清敵之外可冒險救出被稻草包住的友軍，換取本局合作效果；獎勵與風險入場前可看見。
- **石橋選路：**安全路徑與精英挑戰二選一，提供不同升級偏好；兩條路都接回原故事節點。
- **鐘樓守護：**在有限時間內保護／啟動目標，讓敵人方向與玩家站位出現變化。

先採少量手工設計、可重現的模組；沿用無盡已存在的種子生成能力作比較。每種職業都需要可行路線；投射物遮擋、敵人卡位及夥伴追趕一併驗證。

難度先調整近戰、遠程、支援敵人的配合與節奏，沿用現有同時攻擊名額。增加威脅時要保留可辨認的預警與可行撤離空間，並安排戰鬥高峰後的短暫恢復。困難模式可增加招式組合與選擇壓力，數值倍率只作輔助。

現有單種子結果中騎士倒下較多、遠攻較少，只能用作調查線索：三者機器人走法不同，而且固定選第一張卡，不能直接推論該加強騎士或削弱所有遠攻。

### P4：首三分鐘與畫面、聲音

以下秒數為內部設計目標，未經試玩驗證：

| 時段 | 玩家應經歷的事情 | 觀察重點 |
| --- | --- | --- |
| 0–30 秒 | 簡短選角並開始移動，看到停步攻擊的因果 | 是否需要口頭解釋；是否一直移動所以不攻擊 |
| 30–90 秒 | 出現一次清楚預警、第一次有意義的升級 | 是否看懂傷害來源與升級後的變化 |
| 90–180 秒 | 遇到夥伴並完成一次連攜／救援，見到可選風險 | 能否說出這遊戲有甚麼特別 |
| 其後至本局結束 | 小隊成形、精英考驗、頭目與短結算 | 是否想換另一條路線再試 |

首次主線相遇若提前，須同步修改原 1-3 入隊對白，避免重複入隊。劇情可以保留收藏與回看，重玩時控制打斷頻率。升級排隊連續彈窗須量度，避免剛恢復操作又被暫停。

美術下一輪優先補攻擊起手、出手、收招、朝向與腳底位置；命中時點要和判定一致。敵我投射物、危險區及夥伴效果用輪廓與形狀區分，兼顧低特效模式。沿用暖色繪本與狗狗造型。

每個新增系統的可見素材先用 GPT Image 依既有圖集做一致的設計，再處理透明背景、裁切、圖集與動作整合；所有成果以遊戲內實際截圖／影片驗收。生成概念圖本身不代表動作已接入。

配樂已換成 15 主軌與 12 伴奏；下一步安排真人連續聆聽、音效優先級與音量平衡測試，重點觀察循環疲勞、攻擊提示被蓋過及配樂切換突兀。增加音量滑桿、震屏／閃光調節、字級與清晰目標提示。

| 遊玩節奏 | Demo 一輪約 10–15 分鐘為暫定目標；鼓勵第二種打法 | 以短關卡組成完整冒險，允許可靠中斷與續玩 |
| 介面 | 先測桌面寬版布局及全螢幕；戰鬥區擴寬需另測近遠攻平衡 | 安全區、拇指遮擋、不同長寬比、字級 |
| 操作 | 鍵盤／手把從標題到結算完整可用、改鍵、焦點與熱插拔 | 虛擬搖桿、必殺按鈕、回前景後的輸入與暫停 |
| 平台品質 | Windows 實機；後續 Steam Deck／Proton 實測 | iPhone 真機、背景終止、效能、溫度與耗電 |
| 語言 | 繁中保留，英文與簡中先完成 UI 和 Demo；擴充依玩家來源 | 同一翻譯資源架構，依測試地區逐步增加 |
| 長期進度 | 職業精通、故事／同伴圖鑑、外觀與有規則變化的挑戰 | 同樣的可選長期目標，避免把每日登入當作核心趣味 |
| 發現遊戲 | 真實玩法預告、Coming Soon、試玩反饋、願望清單、合適時機的 Next Fest | TestFlight 試玩、準確產品頁與預覽、在成熟版本提交推薦提名 |

Steam 的桌面需求有 Valve 官方指引支持，但表中開發順序與商業模式仍是本案建議。桌面重排第一階段維持原判定區作對照；寬戰場是另一個需測試的規則變體，避免只拉伸背景便改變射程優勢。

平台功能如雲端存檔、成就或商店購買應在核心存檔、內容與平台帳號準備好後整合。現有離線版本不需要為試玩加入帳號或即時服務。

## 6. 用試玩決定是否繼續加大投入

第一輪找 12–20 位未參與開發、符合目標受眾的玩家作形成性試玩；這個樣本只用來找到明顯問題。之後擴大獨立樣本，再估計留存、購買意願與市場轉化，不能把親友評分或少量機器人結果當市場證明。

先固定測試版本、平台、起始永久升級、種子與任務。玩法對照採相同環境、交錯遊玩次序；一次重點比較一項變更。機器人加入多種技能選擇與種子，用來找卡關、無效配搭及極端數值，人類試玩負責回答是否有趣。

| 指標 | 清楚的定義／收集方法 | 提案門檻或用法 |
| --- | --- | --- |
| 理解操作 | 無教練提示下，玩家能自行移動、停步攻擊並避開一次可見預警 | 首輪暫以 80% 為改版目標，報原始人數 |
| 升級理解 | 選後能指出該升級改變了甚麼，以及自己為何選它 | 暫以 70% 為目標；記錄看不懂的具體卡片 |
| 自發重玩 | 固定試玩結束後，明確告知可離開且沒有重玩獎勵，仍自行開始新一局的人數／合資格人數 | 暫以 50% 為進入公開 Demo 的方向性門檻 |
| 玩法差異 | 同職業兩路線的停步時間、技能使用、受擊來源及玩家描述 | 兩路線要有可辨識差異；完成時間相同不代表相同玩法 |
| 公平性 | 倒下前能否辨認威脅；已看到預警時是否存在可行閃避 | 逐段回看，先修不可讀／不可避的事件 |
| 回來玩 | 自願測試者是否在約定觀察窗內自主再次開啟；按新舊玩家、平台與來源分組 | 首輪先建立基準；不使用無來源的 D1 40%／D7 15% 當通用標準 |
| 可靠性 | 崩潰、卡關、配搭丟失、重複領獎與輸入失效 | 發佈候選版不應存在已知可重現的阻斷問題 |
| 市場興趣 | 商店流量、Demo 開始／完成／重玩、願望清單變化、定價概念反饋 | 分開衡量；不能把各渠道總數直接當同一批人的轉化漏斗 |

以上比例是**本專案暫定決策門檻，不是業界已驗證標準，也不是熱門遊戲保證**。小樣本報「幾人／總人數」並描述招募偏差；沒有足夠資料時不要為了湊門檻反覆改定義。

建議試玩報告先留在本機，玩家自行選擇匯出；記錄版本、遊戲內時間、種子、職業、關卡、卡片選擇、受擊來源與中斷點即可，不加入個人資料或裝置識別碼。這是待開發的本地工具，現在尚未建立。

## 7. 可交付的開發批次與停止條件

| 批次 | 可檢查的交付物 | 進入下一批的條件 |
| --- | --- | --- |
| 0.4-A：保留成果 | 冒險檢查點、舊檔相容、獎勵一致性、明確繼續位置；釐清並修整既有清理警告 | 中斷情境矩陣全部按新合約通過；測試不再把重置配搭當成功 |
| 0.4-B：第一個有差異的職業原型 | 先完成一職業兩路線、清楚選卡與一組同伴連攜，加入本地試玩摘要 | 玩家能理解差異；無無效卡、無限連攜或保存遺漏 |
| 0.4-C：完整第一章 Demo | 三職業六路線、18 個核心節點上限、三類遭遇模組、一次可選風險、首三分鐘、頭目及短結算 | 形成性試玩顯示可讀、公平、有人主動重玩；未達標先回頭改核心 |
| 0.4-D：桌面展示品質 | 完整手把、改鍵、版面與聲音設定、Demo 英文／簡中、Windows 實機；真實玩法短片與產品頁草稿 | 宣傳中的機制均可在 Demo 重現，操作與技術阻斷問題已解決 |
| 後續：跨章與手機 | 六章配搭回歸、長期精通／外觀、iPhone 真機與 TestFlight 流程 | 根據實際重玩及平台資料決定擴張；另核對當時上架要求 |

目前不用同時開發多人大廳、賽季、排行榜、更多職業或更多章節。它們都會增加測試與內容成本；應等重玩價值得到證據後，再按明確目的選擇。

## 8. 市場驗證與宣傳安排

1. 先做能從真實玩法看懂的 10–15 秒片段：走位引導敵群、夥伴成功擋箭、職業連攜清場、可愛反應。測試觀眾能否說出玩法與特色。
2. 展示品質達標後準備 Coming Soon 頁與 Demo，使用實際可玩的素材；發布頁面、影片及聯絡創作者是另外的執行工作，本次沒有執行。
3. 收集願望清單與 Demo 反饋，但不要設一個「到某數字必上熱門」的公式。Valve 說明大多數演算法曝光並不直接由願望清單決定；購買、遊玩、語言與標籤等亦重要。[Steam 曝光文件](https://partner.steamgames.com/doc/marketing/visibility)、[願望清單文件](https://partner.steamgames.com/doc/marketing/wishlist)。
4. Next Fest 的現行一般規則是每個遊戲只能參加一次，需要公開的本體商店頁與可公開試玩的 Demo；應先看準備程度再選場次。本次沒有報名或承諾日期。[官方規則](https://partner.steamgames.com/doc/marketing/upcoming_events/nextfest)。
5. App Store 路線先取得可靠 TestFlight 版本，再準備推薦提名。Apple 考慮整體體驗及多項遊戲品質，提名不保證推薦。[Apple 官方說明](https://developer.apple.com/app-store/getting-featured/)。

舊 `MARKET_STRATEGY.md` 中「目前全部程式繪圖」「之後再補第二、三章」與現在版本不符；無來源的留存基準、最高收入／商業模式概括及未驗證的故事時長也不宜沿用。本次以此份可追溯方案取代那些預設。

## 9. 技術落點與驗收邊界

- **存檔：**`game/flow/save_store.gd`、`flow_main.gd`、`RunProgression`；新資料合約、升級轉換及獎勵去重先確立。關卡重試快照可作設計參考，不能直接當完整持久化功能。
- **職業路線：**擴充 `TrickData` 與資料資源，加入職業／路線適用性、互斥與前置條件；抽選、屬性重算、進化及存檔共用同一規則。
- **連攜：**沿用 EventBus；同伴成功防禦提供事件，職業效果透過明確觸發條件與冷卻管理，避免 UI 直接修改戰鬥狀態。
- **關卡：**在 `LevelData` 與流程層定義目標／路徑；掉落、勝利條件、重試及存檔必須一致。
- **呈現：**`ui/illustrated`、`ui/screens`、`ui/audio` 與輸入設定；保持傷害、預警與動畫時間一致。
- **驗證：**功能回歸與資料有效性、自動通關覆蓋、人類試玩、平台實機、宣傳素材核對各有不同用途，結果分開保存。

本文沒有評估市場規模、買量成本、團隊產能或實際收入；亦未調查代表性玩家評論樣本。商業模式、工期與定價應在 Demo 的品質及受眾反饋更明確後決定。
